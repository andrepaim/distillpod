# Working on DistillPod

## Default issue-handling loop

- When asked to handle repository issues, work through the authorized queue autonomously: select one eligible issue, complete it, refresh the queue, and repeat until no eligible issues remain. Do not ask for confirmation between issues already within the user's authorized scope. A request to edit this policy alone does not start an issue-processing run.
- Select the highest-priority ready issue using the repository's established priority and readiness signals; prefer work that unblocks other issues and use oldest-ready first when priorities are equal. An eligible issue has clear scope and acceptance criteria, satisfied dependencies, the necessary authorization, and no active owner in another session. Do not treat every open issue as approved work or invent product decisions to make it ready.
- Claim the issue in the tracker and record the plan before implementation. Keep at most one active issue per session and respect other sessions' ownership. Split oversized issues into small, independently verifiable increments without closing the parent before all its acceptance criteria are met.
- Carry each issue through the applicable engineering workflow below. Features and bug fixes require planning, a separate branch/worktree, TDD for testable behavior, relevant automated checks, applicable emulator acceptance, and physical-device validation when required by the risk assessment below. Documentation-only issues follow the documentation validation exception under Evidence.
- Completion includes review, integration with current `origin/main`, required validation of the combined code, a merged pull request, and successful CI on the combined commit. A local implementation, passing branch checks, or a pushed branch alone does not complete an issue. Link the PR to the issue and record the tested revision, checks, results, and limitations; close the issue only when its acceptance criteria and required validation are satisfied.
- If an issue needs clarification, an unavailable device, separate authorization, or another unmet dependency, record the concrete blocker and the next action needed in the tracker. Leave it open, release ownership when appropriate, and continue with independent eligible work. Do not repeatedly retry an unchanged blocker, bypass checks, or silently abandon unfinished work.
- Refresh priorities, dependencies, and ownership after each issue. Stop when the user asks, the authorized scope is exhausted, or no eligible issues remain; report completed issues and remaining blockers. Queue exhaustion does not mean all open issues are resolved. Never create a release, bump release versions, tag, or publish an APK as part of the loop without a separate explicit release request.

## Production error triage

- When asked to review Sentry or production logs and file issues, investigate and create or update actionable tickets within that scope. A monitoring-and-filing request alone does not start the issue-handling implementation loop or authorize fixes, deployments, releases, or monitoring/account changes. Editing this policy does not start triage or schedule recurring work.
- For recurring triage, prefer daily reviews and an additional review after releases. Record the last completed review window so later runs can continue with an overlap for delayed delivery. Include new errors, regressions, and persistent unresolved failures; do not restrict review to newly created Sentry issues.
- Define and record the projects, environments, explicit UTC time range, release versions, and query limits before investigating. If no previous review exists, start with the last 24 hours and a seven-day lookback for persistent unresolved problems. Separate deliberate test/development traffic from real usage. An event received after a release may describe an older installation or an earlier incident; inspect the affected version and original observation time separately from ingestion time.
- Review crashes, Android ANRs, handled failures, and available operation/performance evidence. Prioritize data loss, security impact, blocked playback/capture/transcription/distillation, severity, recoverability, recurrence, and affected users or sessions when measured. Raw event counts alone do not establish impact; one serious failure can warrant a ticket in a small alpha. Expected cancellations or network/power waits are not automatically bugs, but repeated failures or poor recovery can be actionable.
- Correlate errors with available logs, breadcrumbs, traces, and code using the supported installation/session/request/operation identities and explicit dependency links. Follow the [diagnostic evidence boundaries](docs/android/cloud-diagnostics.md) and [investigation workflow](docs/android/distillation-investigation.md). Nearby timestamps, similar messages, or a shared transcript revision alone do not prove that events belong to one incident. Keep observed facts, causal hypotheses, and missing evidence distinct; do not invent historical fields or reproduction steps.
- Check telemetry health and coverage: consent, installed instrumentation version, offline delivery, sampling/admission limits, dropped events, retention, query caps, pagination, and API failures may limit visibility. Use bounded reads and follow the [ingestion and quota guidance](docs/android/sentry-ingestion-review.md). Report incomplete reads explicitly; absence of an error or terminal event does not prove success, and partial observations do not establish a reliable failure rate.
- Search existing repository issues and relevant fixes before filing. Update an existing ticket when it covers the same supported failure; link related findings without asserting an unproven common cause. Compare the affected release's code with current `origin/main` and published fixes. Distinguish an unfixed regression from a fix implemented but not yet published or installed; do not dismiss ongoing impact on older clients.
- Each new ticket must state the user-visible failure and expected behavior, priority with rationale, affected versions/environments, first/last observed times, frequency or impact within the reviewed window when available, evidence links, reproduction steps if known, suspected cause with confidence, and concrete acceptance/validation criteria. A confirmed actionable failure can be filed without a known root cause or local reproduction. For insufficient evidence, document the gap and next investigation step; create an instrumentation/investigation ticket only when that gap warrants work.
- Keep raw exports, personal content, credentials, and installation/session/operation references private. Public tickets and PRs should contain sanitized summaries and appropriate access-controlled evidence links, not raw log dumps. Follow existing diagnostic redaction and private-output requirements.
- Finish each review with the scope and coverage limitations, findings, tickets created/updated, deferred findings with reasons, and urgent problems requiring attention. After an authorized fix ships, validate the affected flow and review subsequent events from the corrected release before marking the problem verified; record insufficient usage or telemetry as a limitation. Use immediate alerts for urgent actionable failures when configuring an authorized monitoring routine; routine triage does not replace incident response.

## Default feature workflow

- Treat every feature request as authorization to carry the feature through planning, implementation, validation, and merging into `main`. Follow this workflow unless the user explicitly changes its scope; release publication always requires a separate explicit request.
- Complete a plan before implementation. Define the intended behavior, acceptance criteria, affected components, compatibility and data risks, implementation steps, and a per-change risk assessment with the required automated/emulator/physical-device validation. Scale the detail to the change, resolve material ambiguities before dependent work, and update the plan when implementation reveals new information.
- Implement on a short-lived feature branch in its own Git worktree, following the parallel-development rules below. Split larger features into small, independently verifiable increments.
- Use test-driven development for testable behavior: write a meaningful test, run it and confirm it fails for the expected reason, implement the behavior, then refactor with tests passing. Cover relevant failure cases and regressions. For visual-only or exploratory work where an automated test would add little value, explain the limitation and define concrete acceptance checks; do not add tests that merely mirror the implementation.
- Before merging each feature, pass the relevant automated checks, applicable emulator acceptance, and physical-device checks required by the risk assessment below. Record the tested revision, environment/device, scenarios, results, and limitations. Historical phone results do not satisfy required physical-device validation. If a required device or check is unavailable or fails, report the blocker and leave the feature unmerged.
- A feature request authorizes non-destructive installation and validation on the USB-connected phone. Use a compatible development build that preserves the installed app's signing identity, upgrade compatibility, and local data; this is not release publication. Preserve accounts, models, queue, downloads, and listening state. Never uninstall, clear app data, run emulator-only destructive fixtures on the phone, or bypass signing/upgrade safeguards to complete validation. Destructive tests, live-account changes, paid services, and backend/schema deployment still require explicit authorization.
- Once acceptance criteria, review, and required checks pass, integrate current `origin/main`, review and validate the combined code as described below, and merge through a pull request. Verify CI on the combined commit. Do not stop at implementation or an unmerged feature branch when the authorized workflow can be completed.

## Risk-based validation

- Assess each change explicitly in its plan and PR: affected behavior, hardware/platform and upgrade/data-preservation risks, required checks, and why the chosen evidence is sufficient. Reassess after scope changes or integration with current main; do not classify an entire issue queue as low risk.
- Relevant automated checks, review, current-main integration, and applicable emulator acceptance remain required. Lower-risk UI organization, pure business logic, or content-free reporting may use suitable automated/emulator evidence without a physical phone when the rationale and remaining limitations are recorded. Documentation-only work retains the Evidence exception below.
- Require physical-device validation when affected behavior depends on real hardware, OEM/platform differences, or conditions an emulator cannot reliably establish. This includes Bluetooth/headset/audio routing, background execution and battery/power behavior, runtime permissions and notification/system Settings behavior, manufacturer-specific behavior, and relevant in-place upgrade/data-preservation risks. Use the affected phone/accessory and feature-specific protocols; emulator simulations do not establish these results.
- Judge actual behavior and dependencies, not the label or size of the diff: moving a settings section may be low risk, but changing a permission recovery flow is not covered by that example. Content-free reporting is not automatically low risk if it changes background work, persistence, or data handling. Keep applicable feature-specific physical acceptance gates.
- Do not silently waive failed checks or device-dependent cases. Record concrete blockers and required next steps, leave the affected work unmerged, and continue independent eligible issues. This policy does not change device-data safeguards, security/privacy rules, live-account or production-data authorization, deployment permissions, or release gates.
- See [validation planning](docs/development.md#choose-validation-for-the-change) for practical evidence guidance.

## Parallel development

- Use a separate short-lived branch and Git worktree for each independent change, starting from current `origin/main`. Never switch branches, alter unrelated edits, or run concurrent Gradle builds in another session's worktree.
- Keep changes small and merge completed work frequently. Split larger features into safe increments; use temporary feature flags when unfinished behavior needs to land disabled.
- Before merging, fetch current `main`, integrate intervening changes, review the combined diff, and rerun checks relevant to the resulting code. Separately passing feature branches do not establish that their combination works.
- Keep `main` releasable. Follow [development and validation instructions](docs/development.md), and verify CI on the combined commit. Fix or coordinate a revert of regressions promptly; do not publish a failing revision.
- Commit only the intended task files. Prefer pull requests for integration; an explicit instruction to commit and push to `main` authorizes that route. Never force-push `main` to resolve concurrent changes.

## Release ownership and authorization

- Release creation and APK publication require an explicit user request; never trigger them automatically after feature completion or a merge/push to `main`. Feature work must not independently bump release versions, create release tags, or publish assets.
- Designate one session as the release owner. It coordinates version fields in `gradle.properties`, `docs/releases/current.md`, release tags, and publication. Feature sessions document behavior and validation without independently changing release metadata unless assigned that work.
- An explicit request to publish a new APK authorizes the release owner to complete the [release checklist](docs/releases.md), including pushing the release commit/tag and publishing verified assets, without asking for the same authorization again. Report concrete blockers instead of bypassing checks.
- Every APK publication must follow `docs/releases.md`, the authoritative release procedure. Review all changes since the last published APK, including features, fixes, compatibility changes, and known limitations. Do not use stale release notes or treat an unpublished tag as a published release.
- Preserve in-place upgrade compatibility: application ID, retained signing identity, increasing version codes, local data migrations, backup formats, and sync behavior with older installed clients.
- Publication does not implicitly authorize installing on the owner's phone, destructive device tests, live-account actions, paid services, or backend/schema deployment. Follow existing task authorization and the relevant device/cloud instructions.

## Evidence

- Distinguish implemented behavior, automated checks, emulator checks, and physical-device validation. Record the revision and limitations of evidence; historical device results do not validate every later change.
- For documentation-only changes, review accuracy, local links, and `git diff --check`; a full local Android build is unnecessary unless build behavior also changes. CI still runs according to the repository workflows.
- Keep credentials, signing keys, personal content, and device state out of commits, logs, and CI artifacts.
