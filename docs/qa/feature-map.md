# DistillPod feature map and test coverage

This map lists every user-facing feature of DistillPod, the tests that cover it today, the gaps, and the problems found while reading the code. It is the starting point for the beta-readiness test effort.

Source revision: `main` at `607d94c` (November 15, 2026). Each area was mapped by reading the app code, its tests and the docs. Nothing here comes from running the app, except where a row says so.

## How to read it

Each area table has one row per user action or behaviour, with these columns:

- **Risk:**
  - **H**: data loss, blocks the core loop (subscribe → play → transcribe → distill → share), affects the account or money, or leaves a hard-to-recover state.
  - **M**: a visible malfunction with a workaround.
  - **L**: cosmetic.
- **Unit tests:** JVM and Robolectric classes in `app/src/test` and `core/src/test`.
- **CI emulator tests:** device tests that CI runs on every full validation:
  - `scripts/emulator-tests.sh`;
  - the scripts it calls at the end, `android-auto-tests.sh` and `notification-device-tests.sh`;
  - the voice phase, `voice-device-tests.sh`;
  - the cloud phase under Firebase emulators, `sync-device-tests.sh`;
  - the startup phase, `startup56-emulator-tests.sh`.
  A class excluded by `-e notClass` in `emulator-tests.sh` still counts here if one of these scripts runs it.
- **Opt-in / phone-only tests:** device tests no CI phase runs. They need a live account, real YouTube, a long timed trial or a physical phone. Examples: `Live*DeviceTest`, `AuthNetworkDeviceTest`, `PlaybackReliabilityDeviceTest`, `FullEpisodeDeviceTest`, `YouTubeAcceptanceDeviceTest`, `QueueControlsPhoneDeviceTest`, `CloudQueueChoicePhoneDeviceTest`.
- **Real device needed:** whether an emulator can establish the behaviour at all. Examples where it can't: Bluetooth, OEM battery management, Android Auto, live accounts, real networks.
- **Gaps:** edge cases to try. They double as test charters.

**Suspected bugs** come from reading the code and are not confirmed unless marked otherwise. Each needs a reproduction before it becomes an issue.

What the numbers say:

- **Automated coverage is broad.** About 1,100 unit tests and roughly 150 CI device tests touch almost every feature. Only 10 of 203 features have no automated test at all.
- **More than half the features need a real phone to be trusted.** Most automated tests use fakes for the network, the AI and the account. What they can't establish is behaviour under:
  - real Bluetooth, calls and audio focus;
  - Doze and OEM battery management;
  - Android Auto;
  - live ChatGPT and Google accounts;
  - real feeds and CDNs;
  - signed in-place upgrades.

  That is where beta testing time should go.
- **15 high-risk features have no CI device test:**
  - **Audio focus during calls and navigation prompts** (PLY-25) and **pausing when headphones disconnect** (PLY-26) have no test of any kind.
  - **Pending ChatGPT sign-in recovery** (AI-02) and **the selected AI model** (AI-11) also have no test of any kind.
  - **OPML import** (LIB-31) and the **local recovery copy of a backup** (DAT-08) are only unit-tested.

## Next steps

1. **Verify and file.** Reproduce the top findings, on an emulator where possible and on the S22 otherwise. File each confirmed one as a GitHub issue with its feature ID, then the remaining suspected bugs by area.
2. **Close the automated gaps.** Add tests for the high-risk rows with no CI device test, and a regression test for every fix.
3. **Write real-device test charters.** Turn the Gaps column of every row marked as needing a real device into charters for the S22 and S25. Start with playback (PLY-22 to PLY-30), the in-place upgrade (DAT-26) and backup/restore round trips (DAT-02 to DAT-13).
4. **Run a release-candidate trial.** Use the candidate daily on both phones with diagnostics on, against the exit criteria agreed for beta.

### 1. Suspected bugs or risky code (suspicions, not confirmed by running)

- **Unsubscribe can be undone by a refresh (D/PodcastRepository.kt:215).** On HTTP 304 the code writes back the podcast row it read at :198, before the network call. If the user unsubscribes during that request, the show silently becomes subscribed again. That write skips the sync outbox, so this phone and the cloud disagree. The other refresh branches re-read the row inside a transaction.
- **Rotating enclosure URLs wipe state (D/PodcastRepository.kt:238, 249–254).** An enclosure counts as "changed" when the raw URL string differs. Feeds with rotating tracking or signed query strings would, on every refresh, drop the download link (leaving the file orphaned), reset the download state and mark transcripts/analyses stale.
- **Feed refresh jobs are never retried (work/AppJobs.kt:182).** `LibraryWorker` retries only downloads. A transient error on the first fetch after a directory Follow (D/PodcastRepository.kt:154) leaves the show empty until the next periodic refresh.
- **Wi-Fi-only also blocks background feed refresh (work/AppJobs.kt:64).** The periodic refresh honours `wifiOnly`, which defaults to true, so feeds never refresh in the background on mobile data. The setting's text only mentions downloads and transcripts, and one-time refreshes ignore it (AppJobs.kt:55).
- **"Add feed" errors are generic.** `check(...)` (D/PodcastRepository.kt:182), `error("Missing RSS channel")` and SAX parse errors all map to "The operation could not finish. Please retry." in `safeFailure` (D/MediaRepository.kt:331). The intended "Could not load that feed. Check the URL…" text is never shown.
- **"Feed refresh finished" always appears (F/AppViewModel.kt:149–152 with PodcastRepository.kt:327–331).** `refreshAll` swallows every per-feed error, so the message shows even when all feeds failed.
- **One bad OPML entry aborts the whole import** (core Opml.kt:23 `require`, and `publicHttpUrl` inside the transaction at PodcastRepository.kt:315).
- **Imported feeds can miss the refresh (F/AppViewModel.kt:250).** Import enqueues `"refresh"` with KEEP. If a refresh-all is already running, it took its podcast list before the import, so the new feeds wait for the next periodic run.
- **Queue snackbar wording (F/AppViewModel.kt:172; ProductApp.kt:512/575).** Undo goes through `vm.enqueue`, which then shows "Added to queue/play next". Enqueuing the current episode does nothing (PlaybackRepository.kt:72) but still reports "Added to queue".
- **Unsubscribe is not atomic (F/AppViewModel.kt:180–186).** Queue removal and turning automation off happen before `podcasts.unsubscribe`. A failure or process death in between leaves the show followed, with automation off and its episodes gone from the queue.
- **Duplicate subscriptions possible (F/SearchUi.kt:95 `existing()`, PodcastRepository.kt:150 exact `podcastByUrl`).** A directory URL that differs only by http/https or a redirect shows "Follow" again and creates a second subscription.
- **Accented titles sort after Z.** `lowercase(Locale.ROOT)` in D/ShowLibrary.kt:49 and `COLLATE NOCASE` in D/AppDatabase.kt:117 put "Ágora" after "Z" in Your shows and the Library rail.
- **Library search has no accent folding (F/LibrarySearch.kt:46–62).** Show and episode matching is case-insensitive `contains` only.
- **HTML entities show literally (core Feed.kt:19–21).** `plainDescription` decodes only 6 named entities, so `&#8217;`, `&ccedil;`, `&atilde;` inside CDATA descriptions appear as-is (common in Portuguese feeds).
- **iTunes search fixed to Brazil (D/PodcastRepository.kt:121).** `country=BR` may hide shows unavailable in that store.
- **One filter for all pages (F/AppViewModel.kt:20).** The Library filter value is shared by the Library tab and every show page.
- **Move up crosses into History (F/ProductApp.kt:738).** `canMoveUp = index > 0` lets "Move up" on the first Up next item swap it with Now playing, sending it into History.
- **Suggestion follows are not sync-approved (F/ExploreUi.kt, Follow button).** It uses `subscribe()`, not `follow(publicSource=true)`, so these public directory feeds are not approved for sync, unlike a Follow from search.

### 3. Background work in this area

- **`refresh-periodic`**
  - Periodic `LibraryWorker` (kind=refresh, runs refresh-all).
  - Interval = `refreshHours`; network UNMETERED if Wi-Fi-only, else CONNECTED.
  - KEEP when unchanged, UPDATE when the interval or network changes; cancelled when Refresh subscriptions is off.
  - Configured at startup (via `configureNetworkPolicy`) and on settings changes.
- **`refresh`**
  - One-time refresh-all, KEEP, CONNECTED.
  - Triggered after OPML import.
- **`refresh:<podcastId>`**
  - One-time, KEEP, CONNECTED.
  - Triggered after a directory Follow (`onFeedNeeded`) and when automation is enabled.
  - Never retried.
- **`show-automation`**
  - One-time `ShowAutomationWorker`, APPEND_OR_REPLACE, no constraints, up to 3 retries.
  - Started by the in-process `automationKickRequests` flow (500 ms debounce, ignores position-only writes).
  - That flow starts at app startup.
  - The worker in turn queues `download:<id>`, transcription and analysis work (other areas).
- **`recommendations`**
  - One-time `RecommendationWorker`, APPEND_OR_REPLACE, CONNECTED, tag `recommendation:<request>`, 180 s timeout.
  - Interrupted runs are marked failed at startup.
- **Subscription sync kick** (`syncAccount.kick()`) runs on every follow, unfollow or import. It belongs to the sync area.

### 1. Suspected bugs or risky code (suspicions, not confirmed)

1. **Previous button restarts the episode when capture is off** (`auto/AutoLibraryCallback.kt:187`, `playback/PlaybackControls.kt:24-26`). With headphone capture off, `onMediaButtonEvent` returns false, so Media3 runs its default `seekToPrevious`. Past 3 s that jumps to 0:00, and the seek checkpoint then saves ~0 as the episode's position. Removing Previous/Next only applies to the notification controller, so earbuds, AVRCP and Auto steering-wheel buttons still trigger it. HeadphoneDistillDeviceTest:146 expects exactly this (`currentPosition < 1000`). An accidental press means lost progress.
2. **Distill button label changes after the first save** (`AutoLibraryCallback.kt:254` vs `:66`). After a capture the custom layout resets to "Distill" instead of "Distill last 60 seconds". This affects car/legacy layouts and how TalkBack reads it. Cosmetic.
3. **Distill can get stuck on "Saving…"** (`AutoLibraryCallback.kt:243-254`). `captureBusy=true` and the "Saving…" layout are set before `request{}`, but the reset sits inside the block's `finally`. If the request job is cancelled while still in `ready.await()` (for example a cold start where the caller cancels the future), the block never runs. Every later Distill would then return INFO_CANCELLED ("Already saving a moment") and the layout stays disabled until the service restarts. Low confidence.
4. **Inconsistent minimum position for a capture.** The session `captureMoment` only rejects position == 0 (`AutoLibraryCallback.kt:241`). The phone UI and the widget require at least 1 s (`features/LibraryUi.kt:71`, `widget/NowPlayingWidget.kt:27`). Headphone, notification and car presses can therefore save a near-empty moment at 0:00.2.
5. **Error text stays after a successful retry** (`playback/PlaybackRepository.kt:124,130`). `refreshState()` keeps `mutable.value.error`, which is only cleared on `onMediaItemTransition`. After a network error, a successful retry with Play on the same episode leaves "Playback stopped. Check your connection…" on screen.
6. **Rapid taps can be silently dropped** (`features/AppViewModel.kt:154-161,263`). `seek`, `skip` and `undoAdSkip` share the busy key "seek"; `speed` and `keepShowSpeed` share "speed". `action()` ignores a call while the same key is in flight, so very fast repeated −10/+30 or preset taps can be lost. The window is small.
7. **Possible battery cost from polling** (`PlaybackRepository.kt:133-136`). The app-scope MediaController polls player state every 500 ms for the whole process lifetime, including overnight background playback while ExoPlayer holds its wake lock.
8. **Sleep timer lost on swipe-away while paused.** PlaybackService has no `onTaskRemoved` override and relies on Media3 1.5.1's default, which stops a non-playing service. `onDestroy` then releases the in-memory timer (`PlaybackService.kt:529`). getting-started.md says the timer "keeps running … with the app closed", so this case is a silent surprise.
9. **Fullscreen overlay icon ignores loading** (`features/VideocastPlayer.kt:213,231`). The overlay uses `state.playing` instead of `playRequested`. While a YouTube stream resolves it shows "Play video", and tapping it pauses (cancels) the pending start.
10. **Phone Ask leaves the podcast paused when the screen locks** (`features/VoiceUi.kt:77`). Activity ON_STOP cancels a phone voice session with resume=false, so locking the screen or switching apps mid-answer stops the podcast. It looks intentional, but users may not expect it.
11. **Headphone voice permission checks don't match.** The settings readiness requires `areNotificationsEnabled()` (`HeadphoneSettings.kt:83`), but `HeadphoneVoiceService.canArm` only checks the runtime permission (`HeadphoneVoiceService.kt:121-123`). The settings status and the actual arming can disagree when the app or its channel is blocked.
12. **Car host validation is open in debug builds** (`voice/VoiceCarService.kt` `createHostValidator`). Debuggable builds accept any host (ALLOW_ALL). Debug only, but worth knowing for sideloaded builds.

### 3. Background/foreground services and permissions

- **PlaybackService** (`MediaLibraryService`):
  - Exported; `foregroundServiceType=mediaPlayback`; intent filters for MediaSessionService, MediaLibraryService and the legacy MediaBrowserService.
  - Uses `WAKE_MODE_LOCAL` and Media3's audio focus and becoming-noisy handling.
  - Rejects untrusted external controllers. Queue and sleep-timer commands are limited to the app's own uid.
  - Media3 posts the media notification (exempt from POST_NOTIFICATIONS).
  - Permissions: `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MEDIA_PLAYBACK`, `WAKE_LOCK`, `INTERNET`, `ACCESS_NETWORK_STATE`. `usesCleartextTraffic=true` allows http audio.
- **HeadphoneVoiceService:**
  - Not exported; enabled only in voice builds; `foregroundServiceType=microphone`. Started only from a visible Activity.
  - START_NOT_STICKY; stops after 5 min idle, when the setting or key is removed, or when the process dies.
  - Holds a 95 s partial wake lock during a question. Notification channel "headphone-voice" (low importance), ids 8301 and 8302.
  - Permissions: `RECORD_AUDIO`, `FOREGROUND_SERVICE_MICROPHONE`, `POST_NOTIFICATIONS` (needed to arm on API 33+), `MODIFY_AUDIO_SETTINGS` (communication-device/SCO routing, `MODE_IN_COMMUNICATION`).
- **VoiceCarService** (CarAppService, category MEDIA):
  - Exported; enabled only in voice builds; requires the `androidx.car.app.MEDIA_TEMPLATES` permission.
  - `minCarApiLevel` is 8 in voice builds, 1 otherwise. Records through `CarAudioRecord`.
  - Uses the automotive descriptor meta-data and a tintable attribution icon.
- **Widget:** `NowPlayingWidgetProvider` is exported for APPWIDGET_UPDATE only. `NowPlayingWidgetActions` is not exported; it uses `goAsync` with a ≤9 s deadline and immutable PendingIntents.
- **AutoArtworkProvider:** not exported; per-URI read grants only for allowed external browsers.
- **MainActivity:** exported, `singleTop`; handles the MEDIA_PLAY_FROM_SEARCH filter and the `openPlayer` extra (from the notification, widget and headphone-voice notification).
- **Overlap (not mapped):** TranscriptionService and WorkManager's SystemForegroundService (dataSync|mediaProcessing) also run alongside playback.

### 1. Suspected bugs or risky code (suspicions only, not reproduced except the known one)
1. **Known waiting_model bug.** A/data/TranscriptionRepository.kt:137: `resumeModel(id)` only resumes rows whose `model == id`. Line 85: `prepareAutomatically` returns early for a waiting_model row with the same fingerprint. A/features/TranscriptUi.kt:79 and :182 give waiting_model no prepare label and only "Download a model". Nothing re-prepares when the selection changes to a model that is ready, or later becomes ready.
2. **Pause download can't stop downloads started by transcription.** AppJobs.kt:75 (`pause`) only cancels unique work `download:<id>`. Transcription downloads through `withDownloadedAudio` (TranscriptionRepository.kt:321). The progress callback at MediaRepository.kt:152 calls `downloadProgress`, an unconditional UPDATE (AppDatabase.kt:160), so it rewrites "downloading" right after the pause. The Pause button looks ignored.
3. **"failed" shown while a retry is pending.** MediaRepository.kt:184 writes "failed" before LibraryWorker returns `Result.retry()` (AppJobs.kt:182), so the UI shows Failed/Resume during backoff. `clearUnusedAudio` (MediaRepository.kt:279) doesn't protect failed partials, so "Clear unused audio" can delete a partial that is about to be retried.
4. **Settings toggles don't reconfigure queued transcription work.** AppViewModel.kt:190-196: only "wifi" calls `configureNetworkPolicy`; "charging" and "onlineTranscripts" only call `configureRefresh`.
   - Queued `TranscriptWorker` requests keep their old `requiresCharging`.
   - The worker path (`process`) never re-checks `chargingOnly`, so one chunk can run on battery after you enable it.
   - After disabling it, work waits for a charger until the next activity resume.
   - Rows with `lookupOnline=true` keep requiring network after the lookup is turned off (TranscriptionConstraints.kt:11).
5. **Resume silently restarts after a model or language change.** TranscriptionRepository.kt:97-98 reuses the row only if model and language match. Otherwise lines 115-117 create a new revision and delete the saved segments and coverage, while the UI still says "Resume transcript" (TranscriptUi.kt:81). Model and language are portable synced preferences (AppSettings.kt `flow` combine), so another device can trigger this.
6. **"Transcribe locally again" deletes the current text immediately.** TranscriptionRepository.kt:117 deletes segments at the start, with no confirmation. A ready publisher or local transcript is gone until Whisper finishes, and stays gone if no model is downloaded (waiting_model). Only cached online text survives.
7. **Model downloads are fragile.** AppJobs.kt:182 retries IOExceptions only for `kind=="download"`, so a model fails on the first network blip. MediaRepository.kt:299 passes only `etag`, not Last-Modified. Without a strong ETag the 148 MB partial is deleted on resume.
8. **No way to remove a paused or failed model partial.** ProductApp.kt:837-841: the `else` branch shows only Resume. The .partial file (up to 148 MB) stays and counts toward model storage.
9. **Per-chunk overhead.** TranscriptionRepository.kt:330 calls `verifiedModel` every chunk, which SHA-256s the whole model file (MediaRepository.kt:311). WhisperBridge.cpp:26 reloads the model every chunk. A 3-hour episode is about 90 × (hash + load), which costs battery and time.
10. **Auto language is detected per 2-minute chunk.** Each chunk is a separate `whisper_full` call with `no_context`, so the language can flip mid-episode (ads, bilingual shows).
11. **Reboot recovery.** There is no BOOT receiver. `dispatch` only enqueues WorkManager work if the service fails to start (TranscriptionRepository.kt:143-144), and `recover()` only enqueues when the service isn't running. After a reboot or a kill where `onDestroy` doesn't run, transcription resumes only when the process next starts (opening the app, or the periodic refresh worker).
12. **Cosmetic size mismatch.** The 1/2/5 GB chips are GiB (StorageSettings.kt:60), but `fileSize` is decimal (ProductApp.kt:76), so the screen reads "of 2.1 GB".
13. **Manage downloads lists "Failed" rows with no action** except Open episode (StorageSettings.kt:84-91).
14. **Notification Pause pauses only the current episode** (TranscriptionService.kt PAUSE handler with the episode extra), then `kick()` carries on with the next queued episode.

### 3. Background work
**WorkManager jobs**
- **`download:<episodeId>`** (LibraryWorker, kind=download)
  - Policy KEEP; tags `download:<id>` and the class name.
  - Network UNMETERED if Wi-Fi-only, otherwise CONNECTED.
  - Runs as a foreground service via `setForeground` (dataSync, channel "processing", Pause = cancel PendingIntent).
  - IOException retry while `runAttemptCount<3`, default exponential backoff.
  - A refused foreground start is retried up to 5 attempts (`MAX_FOREGROUND_START_ATTEMPTS`), then the row is paused with a message.
  - Triggers: Download/Resume taps, show automation, `recoverDownloads()` at app start.
  - Constraints are updated in place by `configureNetworkPolicy`.
- **`model:<id>`** (LibraryWorker, kind=model): same constraints and foreground setup, no IOException retry. On success it calls `transcription.resumeModel(id)`.
- **`transcript:<ep>:<revision>:<startMs>`** (TranscriptWorker)
  - Policy KEEP; tags `transcript:<ep>` and `transcript-revision:<ep>:<rev>`.
  - Always requires BatteryNotLow; requires charging if charging-only is on.
  - Requires network only when there is no local file, the source is publisher, or an online lookup is pending.
  - Exponential backoff from 30 s; foreground uses mediaProcessing on API 35+, otherwise dataSync.
  - Enqueued when the direct service can't start, by `recover()`, by `nextForeground` when policy is unmet, and per chunk in the worker path.
  - If the service is running, the worker defers to it (`Result.retry`).
- **`refresh-periodic`**: feed refresh, not in my area, but it uses the Wi-Fi policy and is what restarts the process after a reboot.

**Foreground service**
- **TranscriptionService**: non-exported, dataSync|mediaProcessing, notification ID 27001 on channel "processing" (low importance) with a Pause action (`PAUSE_TRANSCRIPTION`).
- Holds a partial wake lock and has a session limit, both 6 hours. `onTimeout` and the 6-hour limit call `pausePending` with a "resume from saved chunks" message.
- START_STICKY; `onDestroy` calls `recover()`. Started by `TranscriptionService.start()` from `prepare` and `resumeQueued`.

**Startup and triggers**
- DistillPodApplication init: `recoverDownloads()` → `jobs.configureNetworkPolicy()` (downloads, models, transcripts) → `transcription.recover()`.
- MainActivity on RESUMED: `transcription.resumeQueued()`.
- PlaybackService: PlaybackTranscription → `prepareAutomatically` when "Transcribe when playing" is on.
- Show automation (overlap) enqueues downloads and transcripts.

### 1. Suspected bugs or risky code (suspicions, from reading the code; not reproduced)

1. **An unreadable credential vault blocks reconnecting.** `ai/AccountRepository.kt:26` treats a failed `vault.read()` as "not connected". But `connect()` calls `vault.read()` again at line 55, inside its try block, so the error goes to `fail()` ("Sign-in could not finish…"). `AuthSession.exchange` reads it again at line 43. Disconnect (the only thing that clears the vault) is shown only when connected. If the Keystore key is invalidated or `openToken` throws, the user may be unable to reconnect without clearing app data.
2. **Switching accounts shows a misleading error.** `AuthSession.kt:46` throws "Sign in with the previously connected ChatGPT account" when Reconnect is used with a different account. `AccountRepository.fail()` (line ~147) turns this into the generic "Sign-in could not finish. Check the connection and try again." Nothing tells the user to Disconnect first.
3. **A stale or synced model breaks all AI with no visible selection.** `ai/AiGateway.kt:29` requires the selected model to be in the account's catalog. `aiModel` is portable (sync and backup), so a model from another device or a retired one makes every capture, post, analysis and chat fail ("Choose an available AI model in Settings"). The radio list at `ProductApp.kt:813` then selects nothing. Also, `AiGateway.kt:28` fetches `/models` before every completion, doubling HTTP calls and 429 exposure.
4. **The context window can drop the segment containing the tap.** `core/.../MomentContext.kt:40` excludes any whole segment ending after tap+15 s or starting before tap−120 s. Publisher transcripts with long cues can drop the segment that holds the tap. This plausibly explains the live observation that the window trimmed the strongest part of a moment.
5. **No automatic resume after auth or quota recovers.** No code observes `account.connected` or quota recovery to re-enqueue `waiting_auth` or `waiting_quota` rows (`CaptureRepository.kt:149/399`, `EpisodeUnderstanding.kt:217`, `MomentExplanation.kt:37`). Moments captured while disconnected stay "Connect ChatGPT to continue" after connecting until Retry is tapped on each one. It looks intentional (a test asserts there is no automatic retry), but it is a UX trap.
6. **Pause actions overwrite state without checking it is still running.** `AppViewModel.kt:253–256` (`pauseAnalysis`), `260–262` (`pauseReply`) and `269–271` (`pauseExplanation`) write `state="failed"` unconditionally. A tap that races completion can turn a succeeded analysis into failed. The summary is then hidden and "Resume analysis" appears.
7. **Explanations fail when the excerpt contains a link.** `MomentExplanation.kt:30` rejects any report containing `https?://`. If the excerpt itself contains a URL (sponsor reads), a faithful explanation may repeat it and fail every time.
8. **The "excerpt" leak check is English-only.** `SocialComposer.kt:99` (`SOURCE_WORD`) only catches "excerpt". Portuguese captions that say "trecho" (or other source mentions) pass, although the prompt forbids them.
9. **A denied foreground start fails the post.** `SocialPostWorker.kt:42` calls `setForeground` with no handling for a background foreground-service start being refused. `LibraryWorker` handles this via `isForegroundStartRejected`. A refusal (for example, re-enqueue at app start in the background on Android 12+) falls into the generic catch and marks the post failed.
10. **Create post has no dedupe after completion.** `AppViewModel.kt:210` only blocks while the action is in flight. Tapping "Create post" again creates another post and another AI request.
11. **Capture dedupe is narrow.** `AppDatabase.kt:208` dedupes only when the position differs by <1 s within 2 s. Two deliberate taps 1–2 s apart during playback create two moments, each with 2 AI requests.
12. **The delete dialog understates what is removed.** `SavedMomentsUi.kt:298` says insight, quote and versions are removed and posts are kept. Explanations (`research`, CASCADE) are also deleted silently.
13. **Share can use the previous style.** In `PostEditorUi.kt:137`, Share renders `result` from the database. A style swiped just before the `restyle` write lands is shared in the old style.
14. **Latent cascade risk.** `distillations` cascades from episodes, which cascade from podcasts (`AppDatabase.kt:25,70`). `deletePodcast` is currently unused, but any future podcast or episode deletion would silently delete saved moments.
15. **Minor: streaming writes block the network thread.** `EpisodeUnderstanding.kt:183` uses `runBlocking` DB writes inside the streaming `onDelta` callback on the AI executor thread.

### 3. Background work

- **`capture:<momentId>`, CaptureWorker** (`AppJobs.capture`). APPEND_OR_REPLACE, needs network. Enqueued when a moment becomes `queued` (hydrate or generate) and at app start for rows already `queued`. No retry or backoff (always returns success). Cancelled by "Pause generation". Rows left running or reviewing after process death are marked failed at startup (`EpisodeUnderstanding.recoverInterrupted`).
- **`analysis:<episodeId>`, `reply:<messageId>`, `explain:<researchId>`, UnderstandingWorker** (`AppJobs.enqueueAi`). APPEND_OR_REPLACE, needs network, always success, no retry. At startup running rows become failed and queued rows are re-enqueued.
- **`recommendations`, RecommendationWorker.** APPEND_OR_REPLACE, needs network, tag `recommendation:<request>`, no retry. Interrupted runs are recovered at startup.
- **`social:<postId>`, SocialPostWorker** (`SocialPostJobs.enqueue`). APPEND_OR_REPLACE, needs network. Runs as a foreground service (dataSync, channel "processing", notification "Creating your post" with a Pause action). Never retries ("Never silently retry…"). At startup, active-stage posts with no pending work are re-enqueued with KEEP-like logic. A post found in a non-`queued` active stage is marked failed ("Creation was interrupted…").
- **Not WorkManager:**
  - OAuth sign-in coroutine in the app scope (loopback listener, 10-minute timeout, waits for the app to be in the foreground).
  - `refreshModels` coroutine (on opening Settings › ChatGPT and after connecting).
  - Background capture save and prepare from PlaybackService, AutoLibraryCallback and the widget.
  - `captures.resumeSaved()` at startup.
  - `captures.transcriptUpdated()`, called from `TranscriptionRepository` (lines ~293/336/381) when a transcript publishes.

### 1. Suspected bugs or risky code (suspicions)
1. **Backups from a newer app fail with an unhelpful message** (`data/LibraryBackup.kt:60`, `:69`, `:243`). Export hard-codes `databaseSchema=7`, and preview accepts 1..7 but requires an exact column match. A backup from a newer app with an extra column fails with "Backup columns do not match this version" instead of "update the app". Every future column must also remember to bump the marker. Line 57 uses `System.currentTimeMillis()` instead of the injected `now`.
2. **One missing or corrupt post image blocks every backup** (`data/PostBackupBundle.kt:30`, with `sharing/PostAssets.kt:25`).
   - `assets.read()` throws for a missing or corrupt image, which aborts both Back up now and the standalone export. `SocialResultTest` asserts this failure.
   - The FileNotFound case surfaces as "The backup file is unavailable. Check the file provider's account…" (`ManagedBackups.kt:73`) or "The file provider could not complete this transfer…" (`BackupDocuments.kt:58`). Both blame the provider wrongly.
   - The only workaround is to find and delete the post.
3. **Recovery copies are never cleaned up** (`ManagedBackups.kt:42-47`, `:160-166`). Recovery copies (`filesDir/backup-recovery/<hash(uri)>.zip`, up to 64 MiB each, with personal text) are never deleted on Forget, Connect another or Create another. Old copies pile up.
4. **Long write-transactions during export and preview** (`LibraryBackup.kt:35`, `:111`). Both run inside `db.withTransaction` and scan up to 100k rows. Back up now does both, back to back (`ManagedBackups.kt:186-187`). This can stall concurrent Room writes (playback progress, sync) on large libraries.
5. **Retention and "latest" depend on the wall clock** (`BackupArchive.kt:66`, `:73`; `ManagedBackups.kt:190`). They sort by snapshot `at`. A snapshot taken with the clock set to the future always sorts first: it is never evicted and is shown as "Latest available backup".
6. **One startup failure silently breaks the app** (`DistillPodApplication.kt:103-131`). The whole recovery chain sits in a single try. Any exception (`importFeasibility`, `recoverInterrupted`, the WorkManager `.get()`) completes `ready` exceptionally and skips UpdateJobs.configure, transcription.recover, automation.observe and captures.resumeSaved. Every `ready.await()` in workers, PlaybackService and sync then throws. Nothing is shown in the UI and nothing is reported to diagnostics.
7. **Toggling usage statistics discards pending diagnostics** (`Diagnostics.kt:72-74`). `usageConsent()` calls `queue.clear()` and deletes the sentry dir, even while diagnostics stays enabled.
8. **"Source and notices" can crash** (`LicenseAndSources.kt:23-25`). `startActivity` has no try/catch, so it crashes when no browser is installed. It also opens `/releases/tag/v$version`, which is a 404 for unpublished private builds. The About update links do use `runCatching`.
9. **Non-sentry.io DSNs retry forever** (`DiagnosticsUploadWorker.kt:23`). A DSN host not ending in `.sentry.io` fails the require on every run and loops on `Result.retry()`, showing "Waiting to upload".
10. **More than 20 conflicts are hidden** (`sync/SyncEntities.kt:45`). `observeConflicts` uses LIMIT 20 and is not scoped to the bound uid/generation. Also, `observeCount` (pending) includes conflict and upgrade_required rows.
11. **Backup page downloads the whole file on every open** (`ManagedBackupUi.kt:67`). It calls `backups.refresh()`, downloading up to 64 MiB on any network.
12. **"Standalone JSON" export is not always JSON** (`BackupDocuments.kt:79`). It is a ZIP named `.distillpod` when posts have images; the button still says "Export a standalone JSON copy".
13. **Backup operations are tied to the screen** (`AppViewModel.kt:99-100`). They run in `viewModelScope`, so leaving the activity cancels them. Process death during `BackupDocuments.save` leaves a partial new document that is never deleted (the cleanup at `:119` never runs).
14. **Stale docs.**
    - `docs/android/drive-backup.md:39` says backup schema markers 1–4 and Room "currently 8". The code has markers 1–7 and Room 12.
    - `implementation-status.md` says Room 9.
    - `reliability-analytics.md:44` says diagnostics health reports are hourly; the code (`Diagnostics.kt:129`) uses 6 h.
15. **Update choice depends on GitHub list order** (`AppUpdates.kt:42-60`). The first eligible release in GitHub's order wins. A later-published release from an older line (lower versionCode) masks a newer one, and `UpdateChecker.check` then clears the stored update.

### 3. Background work
- **`update-check`**: periodic, 1 day, needs CONNECTED, ExistingPeriodicWorkPolicy.KEEP. Scheduled from the AppGraph startup chain and from the About switch. Cancelled when the switch is off or the build is debuggable. On IOException the worker returns success and waits for the next daily run.
- **`subscription-sync`**: unique one-time, needs CONNECTED, exponential backoff starting at 30 s, `Result.failure` after 8 attempts, 60 s timeout per run. Triggered by `kick()` (300 ms debounce, 2 s max wait; called on resume, library/playback changes, portable preference changes) and by `syncNow()` (replaces a run waiting in backoff). Policy is KEEP or APPEND_OR_REPLACE (one follow-up). Pause cancels it.
- **`subscription-sync-recovery`**: periodic, 15 min, CONNECTED, KEEP. Enqueued when SubscriptionSyncAccount initialises in a configured build. Not cancelled on pause.
- **`diagnostics-upload`**: unique one-time, KEEP, CONNECTED, 10 s initial delay, exponential backoff from 30 s.
- **`diagnostics-recovery`**: periodic, 15 min, CONNECTED, KEEP. Both diagnostics jobs are cancelled when neither consent is on.
- **Startup (not WorkManager):** reconcile the journal, `releaseSessions`, legacy import, recover interrupted AI work, re-enqueue queued captures and active `social:<id>` posts, `recoverDownloads`, `configureNetworkPolicy`, then UpdateJobs.configure, then `transcription.recover` and `ready`. Other jobs (refresh, refresh-periodic, download, model, transcript, capture, AI kinds, show-automation, social) belong to other areas.

### 4. Release/upgrade facts
- **Room:** `AppDatabase` version **12**, `exportSchema=true`, schemas 1–12 in `app/schemas/dev.distillpod.android.data.AppDatabase/`. Migrations run contiguously 1→2 … 11→12 (`AppDatabase.kt:335`). There is no `fallbackToDestructiveMigration`, so a downgrade crashes rather than wiping data.
  - 11→12 adds `localDownloadedAt` / `localCreatedAt`, default 0, meaning "unknown age".
  - Tested by OnlineTranscriptMigrationTest (JVM, 1..11→12) and DatabaseUpgradeDeviceTest (emulator, per schema 1–11).
- **Backup formats:** library format v1 (no preferences) or v2, with backup schema marker 7 on export and 1–7 accepted on import (separate from the Room version). History format 1. Limits: 32 MiB per snapshot, 100k records, 64 MiB archive, 128 MiB expanded, 10 snapshots.
- **Sync:** clients read protocols 1–4 (`SyncCompaction.PROTOCOL=4`). Compaction is off unless built with `-PdistillpodSyncCompaction=true`. Content storage is off (`sync_content_enabled=false`).
- **Version:** `gradle.properties` has `distillpodVersionName=0.29.0-alpha.1`, `distillpodVersionCode=53`; minSdk 29, targetSdk 35.
- **How version codes are validated:** `scripts/release_metadata.py` (run by release.yml) checks:
  - semver name;
  - code in 1..2,100,000,000;
  - tag equals `v`+name;
