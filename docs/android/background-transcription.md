# Transcription with the screen locked

> Historical validation report. Results and commands below apply to the stated
> revision and device. For current behavior, use the [usage guide](../getting-started.md),
> [build instructions](../development.md) and [implementation status](implementation-status.md).

November 4, 2026.

The reported symptom was preparation stopping after the phone locked, with another manual start required. The old implementation already promoted each WorkManager worker to a foreground service, but finished that worker after every two-minute audio window and scheduled another job for the next window. That left execution dependent on another Android scheduling decision between checkpoints. Android 16 also applies JobScheduler runtime quotas to foreground WorkManager jobs. The attached S22 reports API 36. Historical logs from the reported run are unavailable, so this identifies a code-level failure path rather than proving which OS stop reason occurred yesterday.

User-started preparation now starts a dedicated, non-exported foreground service. One session consumes successive windows without scheduling another job between them. Native inference remains on the existing single executor; the service does not run inference on the main thread. Its bounded partial wake lock permits CPU work with the display off. The lock and notification are released when the session stops. The notification can pause the current episode; cancellation reaches both decoding and native Whisper.

The existing two-minute Room checkpoints remain authoritative. Resume keeps the same transcript revision and skips completed coverage; live percentages are never treated as saved text. A sticky restart or returning to the app can pick up queued work. Explicitly paused rows stay paused. A six-hour session limit and Android's foreground-service timeout preserve checkpoints and expose a resumable pause.

Battery, charging-only and network policies still apply. Downloaded audio can be transcribed offline. When a requirement is unmet, deferred WorkManager requests retain Android's constraints. Background work that cannot legally start a direct foreground service also retains that fallback. These deferred requests remain subject to Android scheduling; the direct service is used for the listening-session path initiated while the app is visible. Force-stop and user/system restrictions can still interrupt work.

Android 15+ local inference uses `mediaProcessing` alone, avoiding consumption of the unrelated `dataSync` allowance. Older Android versions use the existing `dataSync` declaration. This does not use a playback or microphone service type for computation. The platform `startForeground` overload is used directly: the AndroidX Core version currently resolved by this project filters out the API 35 media-processing bit. The first emulator trial exposed that incompatibility; an API 35 unit regression now verifies the actual foreground-service type.

### Queue order and wait reasons (#299, November 2026)

Later change, not part of the validation below. The session still prepares one transcript at a time, choosing the next one between chunks. Transcripts the user asked for (Prepare or Resume transcript, Transcribe locally again, or a saved moment that needs the transcript) go first, in the order asked; automatic ones (Transcribe when playing, show automation, a newly downloaded model) follow, oldest revision first. The chunk in progress is never interrupted. The request order is kept in memory only. After the process dies, saved moments that still need a transcript request it again at startup and everything else runs oldest first. The order applies to the foreground session; when Android refuses that session, deferred WorkManager chunks run in the order Android schedules them (#301 covers that path). Each queued row shows its last recorded wait (recomputed since #336, [below](#queued-status-that-follows-settings-and-the-queue-336-november-2026)): behind another transcript (`queued_behind`), charger, low battery, Wi-Fi, offline, a refused background start (`restricted`), or Android's background network block before the audio download (`network_blocked`, #312); the same value is the reason of the transcript's `operation.summary` (outcome `queued` or `waiting`). Before #313 it was also logged as a raw `transcription.queued` line.

### Background starts Android refuses (#301, November 2026)

Later change, not part of the validation below. A transcript deferred to WorkManager (charger, battery, Wi-Fi or a refused direct session) used to retry its foreground start up to five times when Android 12+ refused it in the background, then pause with "Android could not start transcription. Tap Resume to continue from saved chunks." A later attempt is refused the same way, so the chunk now runs at once as ordinary background work without the notification, like an analysis (#84) and a download (#292). It is logged as `transcription.stage` with reason `restricted`, the one stage still logged since #313 (see [cloud diagnostics](cloud-diagnostics.md#background-transcription-volume-313)). The row is never paused for this reason; the next app start resumes rows an earlier version paused with that message (a user's pause, or one whose audio changed since, stays put).

- **One chunk per run.** The worker processes the single two-minute window it was scheduled for, saves its Room checkpoint and enqueues the next window as a new constrained request, as before. It does not loop over the whole episode: without the notification that would be a long, invisible CPU job outside Android's job limits. Power and network settings therefore still apply at every chunk boundary, as in the foreground session.
- **CPU and stops.** WorkManager 2.10.1 (checked in its bytecode) records the worker as foreground work and takes its own partial wake lock (`ProcessorForegroundLck`) before Android refuses the service, and releases it when the worker ends. The job scheduler's own stop of that worker (time limit, lost constraint) is ignored, so the chunk keeps running while the process does. App Pause still cancels it. Doze can disable that wake lock and the process can be frozen or killed; tiny on the S22 measured about 0.15× real time, so a chunk is normally well inside the ten-minute job window.
- **Stops and process death.** A stop before the chunk is saved leaves the row queued with its saved chunks; WorkManager reruns the same request (nothing cancels it) and startup recovery keeps it. At most the current chunk is redone. There is no attempt budget any more: a chunk that regularly outlasts what the background process survives (a slow phone, the Base model, a process frozen or killed once the job window ends) would be redone on each run without pausing. Repeated `transcription.stage` `restricted` events for one revision without new coverage would show it, as would repeated `operation.summary` `running` rows (one attempt per window) for that revision.
- **Order.** Request order (#299) still applies to the foreground session only. On this path each revision is its own WorkManager chain and chunks run in the order Android schedules them; the next visible app start hands the queue back to the ordered session. Carrying the order into WorkManager would mean a worker processing another revision than the one it was scheduled for, or holding job time to wait its turn.
- **Settings.** Turning **Only transcribe while charging** on or off now updates queued requests in place, like the Wi-Fi setting; a chunk already running finishes first.

### Audio downloads Android blocks in the background (#312, November 2026)

Later change, not part of the validation below. A chunk running without its notification can reach an episode whose audio is not on the phone while Android 15+ blocks the app's network (#292). WorkManager 2.10.1 starts constrained requests in the running process when its own trackers see the constraints met, and its network tracker (checked in its bytecode) ignores Android's per-app block. Transcripts run one at a time behind a shared lock, so such a request can start long before its turn and fetch its audio right after another transcript's chunk ends. The download then failed at once and the transcript ended **Failed** with "Could not reach the server. Check your connection and retry."

That download now uses the same check as background downloads (`DownloadNetwork`): when a chunk whose notification Android refused fails to fetch its audio and Android reports the network as blocked, the row goes back to queued with its partial file, records the wait `network_blocked` (shown as "Queued · waiting for network access", the reason of the transcript's `operation.summary`), and the same worker waits outside the transcription lock until the network is usable, then continues. Transcripts whose audio is on the phone run meanwhile. The request's pending job, or opening the app, lifts the block, as for downloads. A pause cancels the wait; a stop of the worker leaves the row queued for WorkManager to rerun. A failure with no reported block (a real outage, a server error, no storage), or one in a chunk that has its notification, still fails with its message. `TranscriptionNetworkBlockTest` covers both paths.

### Queued status that follows settings and the queue (#336, November 2026)

Later change, not part of the validation below. Turning **Only transcribe while charging** (or the Wi-Fi setting) on or off updated the queued requests in place but not the wait their rows showed. A transcript that did not start at once, because another one took the slot, kept "Queued · waiting for a charger" until it started or was requested again; the foreground session corrected it at its next chunk boundary, a WorkManager chunk never did. A transcript behind another said only "after another transcript", so a 12-minute wait on the S22 looked like a stall and was paused and resumed twice.

- **Recomputed waits.** After a settings change, when a chunk starts or ends (in the foreground session or as a WorkManager chunk), and when the app is shown, each queued row's power or network wait is checked again. It becomes the current one (charger, low battery, Wi-Fi, offline) or, when none applies any more, `queued_behind` if another transcript is being prepared, else `scheduled` ("Queued · waiting to start"). A refused start (`restricted`, #301) and Android's network block (`network_blocked`, #312) are kept until the transcript runs, unless a power or network wait now applies.
- **What is prepared first.** Being behind is shown from the live progress the app already has for the running chunk, not stored or polled: while another transcript's chunk runs in the app's process, a queued row without a power or network wait shows "Queued · after another transcript (62%)" on the episode row and `Queued · "<episode title>" is being prepared first (62%). Transcripts are prepared one at a time.` in Transcript tools. The percentage is that transcript's overall progress as its own row shows it, left out while it looks for an online or publisher transcript or has no duration; the title is shortened to 40 characters at a word. Without a known title the sentence from before is shown. Between two chunks the last transcript stays named for two seconds. A row that waited behind one when nothing is being prepared any more shows "Queued · waiting to start".
- **Diagnostics.** Only a recomputed wait that differs from the recorded one is reported, as an `operation.summary` with the new reason (#313): a settings change with N queued transcripts writes at most N lines, none when no wait changed, and the queue's own chunk boundaries add none for unchanged rows. Progress is not reported. `TranscriptionWaitRefreshTest`, `TranscriptionQueuedDiagnosticsTest` and `QueuedTranscriptStatusUiTest` cover this.
- **Unchanged.** Queue order, pause and resume, constraints and scheduling. A deferred request that Android has not started yet still waits for Android; the app cannot tell when that will be, so its row says "waiting to start".

## Comparison with existing projects

Reviewed primary source on November 4, 2026. Repository stars are only an indication of public adoption, not proof of reliability. No external implementation was copied.

| Project | Relevant implementation | What applies to DistillPod |
| --- | --- | --- |
| [FUTO Voice Input](https://github.com/futo-org/voice-input) (~350 stars) | [AudioRecognizer](https://github.com/futo-org/voice-input/blob/master/shared/src/main/java/org/futo/voiceinput/shared/AudioRecognizer.kt) runs model work on `Dispatchers.Default` in a lifecycle scope, with explicit cancellation; its main use is short dictation through an activity or input method. | Background execution and native cancellation are appropriate. Its dictation lifecycle is not evidence that an hour-long file should be tied to an activity or keyboard. |
| [Transcribro](https://github.com/soupslurpr/Transcribro) (~760 stars) | [MainRecognitionService](https://github.com/soupslurpr/Transcribro/blob/main/app/src/main/kotlin/dev/soupslurpr/transcribro/recognitionservice/MainRecognitionService.kt) owns IO coroutine jobs and cancels/releases recognition on service destruction. | Service ownership and deliberate cancellation are common. It is an Android recognition service, not a directly comparable long-file foreground-service implementation. |
| [VoiceSkip](https://github.com/tguillem/VoiceSkip) (smaller project, 8 stars) | [TranscriptionService](https://github.com/tguillem/VoiceSkip/blob/main/app/src/main/java/com/voiceskip/service/TranscriptionService.kt) is a foreground service for audio files, uses a wake-lock manager, a notification/cancel action, and timeout/destruction cleanup. | This is the closest use-case match and supports the dedicated service + CPU wake lock pattern. DistillPod retains its own durable checkpoints and uses the newer media-processing type where supported. |

The authoritative Android references are [long-running WorkManager jobs and Android 16 quotas](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running), [foreground-service types](https://developer.android.com/develop/background-work/services/fgs/service-types#media-processing), [foreground-service timeouts](https://developer.android.com/develop/background-work/services/fgs/timeout), and [wake-lock lifecycle](https://developer.android.com/develop/background-work/background-tasks/awake/wakelock). The direct foreground-service alternative is explicitly described in the WorkManager guidance for Android 16 quota exhaustion.

## Regression checks

`TranscriptionServiceTest` verifies that a session holds and releases its CPU wake lock, that local work is allowed offline, and that charging/low-battery/network requirements are enforced.

`NativePipelineDeviceTest` uses a public-speech fixture on an isolated emulator. It verifies progress before the first checkpoint, pauses after the first saved window, resumes the same revision, removes all scheduled jobs for that transcript, sends the app home, and turns the display off. Both remaining windows must finish before the screen is woken. Saved coverage must be exactly 0–120, 120–240 and 240–330 seconds with real recognized speech.

The targeted API 36.1 emulator regression passed in 58.7 seconds. All 48 core and 86 app JVM tests pass, including the wake-lock, service-type and power-policy checks. All 30 ordinary emulator acceptance tests passed in 160.1 seconds. A final four-test regression passed in 68.8 seconds after adding a real scheduled-recovery handoff check: a worker retains its retry while the service owns inference, then the test cancels all scheduled transcript jobs before locking the display. Debug/release lint, APK builds, 11 release-tool tests, alignment and retained-certificate verification pass. See [validation evidence](evidence/background-transcription-validation.json).

Validation also exposed an existing backup-operation race: earlier temporary-file cleanup could mark a newer operation interrupted. Cleanup is now guarded by its operation identity; the existing recovery and corrupted-provider regressions pass. The screen-off test does not simulate an exhausted Android runtime quota or establish the exact OS stop reason from the reported run. No fixture suite or live-account request was run on the owner's phone.
